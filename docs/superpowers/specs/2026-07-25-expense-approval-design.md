# 지출결의서 전자결재 — 설계

날짜: 2026-07-25 / 승인: 김태정 대리
결정 사항: 지출결의서 전용(범용 결재엔진 아님) · 결재선은 매번 직접 지정(기본값 없음) · 역할은 결재자+협조자 2종 · 양식 본문은 카카오워크와 100% 동일(엑셀 업로드 포함) · 최종 승인 시 `expenses` 자동 등록 · 계정과목은 최종 결재자가 승인할 때 선택 · 문서번호는 `CDV-26-000158`부터 이어받기 · 앱푸시 + 화면 배지

## 문제

지출결의서를 카카오워크 전자결재로 처리해 왔다. 2026-07-25 기준 문서대장에 876건이 쌓여 있고 직원 8명 전원이 쓴다. 방식 자체는 잘 맞아서 그대로 ERP로 옮기려 한다.

옮기려는 이유는 두 가지다.

1. **지출 데이터가 ERP 밖에 있다.** ERP의 `/expenses`는 결재가 없는 지출 기록장(지출·고정비·카드 3탭)이고, 실제 집행 승인은 카카오워크에서 일어난다. 승인된 돈이 ERP에 자동으로 들어오지 않아 이중 입력이 된다.
2. **카카오워크 이탈 대비.** 876건의 결재 이력과 첨부(세금계산서·통장사본·거래명세서)가 외부 서비스에 묶여 있다.

## 관찰한 실사용 패턴

문서대장에서 완료 문서 3건을 상세까지 확인했다. 설계 판단의 근거가 되므로 남긴다.

| 항목 | 관찰 결과 |
|---|---|
| 결재선 | 3건 모두 `기안자 → 조혜진(dawoo-1) 단독 승인`. 대표(김재호)는 결재선에 없음 |
| 결재의견 | 3건 모두 `"대금지급 완료"` — 승인이 곧 실제 송금 실행 신호로 쓰인다 |
| 지급 정보 표 | 이게 문서의 본체. 1~2행 |
| 상세 내용 표 | 3건 모두 비어 있음 |
| 현장 구분 | 정식 필드가 없어 거래처명 칸에 문자열로 섞어 씀 (`신성공사 [단독 화서동 184-342]`) |
| 첨부 | 거의 고정 4종 — 세금계산서 / 사업자등록증 / 통장사본 / 견적서·거래명세서 |
| 제목 관행 | `[업체] 지역 현장명 공사종류 지출결의서` |
| 문서번호 | `CDV-26-000157` = 양식약어 - 년2자리 - 순번6자리 |
| 공람 | 1건에서 사용됨. 협조는 확인한 3건에 없음 |

## 접근 방식과 근거

### 왜 범용 전자결재를 만들지 않는가

카카오워크 전자결재는 양식 빌더, 양식함 관리, 공용 결재선, 부서협조·부서수신, 문서담당자, 권한 관리, 백업까지 갖춘 플랫폼이다. 직원 8명에 부서가 `주식회사 다우건설` 하나뿐인 조직에서는 이 중 대부분이 동작할 대상이 없다. 조직도가 평면이라 "부서협조"라는 개념 자체가 성립하지 않는다.

지출결의서 한 종류만 하드코딩하면 양식 빌더·양식 관리·공용 결재선 관리가 전부 사라진다. 다른 양식이 필요해지면 그때 이 구조를 일반화한다.

### 왜 양식 본문은 카카오워크와 100% 동일하게 두는가

현장·거래처를 ERP DB(`sites`, `vendors`)와 연결하면 계좌번호 자동 입력과 현장별 지출 집계가 가능해진다는 제안을 했으나, **직원이 익숙한 화면을 그대로 유지하는 쪽**으로 결정됐다. 876건을 써온 사람들이 다시 배울 필요가 없다는 이점이 자동화 이득보다 크다는 판단이다.

따라서 지급정보 표의 거래처명은 자유 텍스트이고, 현장 칸은 만들지 않는다. `상세 내용` 표와 엑셀 업로드도 실사용이 없거나 적지만 그대로 구현한다.

이 결정의 대가는 명시해 둔다. **승인된 지출에 현장(`site_id`)이 붙지 않아 현장별 원가 집계가 안 된다.** 필요해지면 지급정보 표에 현장 칸을 추가하는 후속 작업으로 푼다.

### 왜 결재 액션을 서버 API로만 처리하는가

현재 ERP는 프론트가 anon 키로 Supabase를 직접 호출하고 운영 RLS가 실질적으로 꺼져 있다. 이 패턴을 결재에 그대로 쓰면 브라우저 콘솔에서 임의의 결재 레코드를 넣을 수 있다. 그래서 상태를 바꾸는 액션은 전부 서버 라우트를 거치고, 서버가 문서 상태와 결재선을 DB에서 다시 읽어 판정한다.

조회(목록·상세)는 기존 패턴대로 프론트에서 직접 읽는다. 위조 위험이 없고 기존 코드와 일관된다.

### 행위자를 로그인 계정에서 뽑지 않고 화면에서 고르는 이유 (2026-07-30 변경)

**당초 설계**는 로그인 계정의 이메일로 `staff` 행을 찾아 행위자를 확정했다. 결재는 "누가 눌렀는가"가 전부이므로 위조를 원천 차단하려는 의도였다.

**실제로는 동작하지 않았다.** 운영 `staff` 테이블에 이메일이 채워진 사람이 사실상 없었고(9명 중 1명, 그마저 실제 로그인 계정과 불일치), 직원들이 카카오·네이버 계정을 섞어 쓰며 계정도 여러 개다. 이 상태에서는 아무도 기안조차 할 수 없었다. 더구나 기존 ERP의 다른 화면들은 이미 대시보드에서 이름을 골라 `localStorage`에 담아 쓰는 방식이어서, 결재만 다른 신원 모델을 쓰는 것이 사용자에게 일관되지 않았다.

**변경**: 기안자와 결재 행위자를 화면에서 직접 고른다. 서버는 요청 본문의 `actor_staff_id`를 행위자로 받는다.

**남는 것과 잃는 것**을 분명히 해둔다.

- 여전히 **로그인은 필수**다. 세션이 없으면 미들웨어와 각 라우트가 401로 막는다. 외부에 열린 것이 아니라 사내 로그인 사용자 사이의 구분이 사라진 것이다.
- 여전히 **서버가 권한을 판정**한다. 고른 사람이 지금 결재할 차례가 맞는지, 기안자 본인이 맞는지는 DB 상태로 검증한다. 차례가 아닌 사람을 골라 승인할 수는 없다.
- **잃는 것**: 화면에서 다른 직원 이름을 골라 그 사람으로 기안하거나 승인할 수 있다. 결재 이력이 "그 사람이 직접 눌렀다"는 증빙은 되지 못한다.
- **보완**: 행위 시점의 로그인 계정 이메일을 함께 기록한다(`expense_reports.drafted_by_email`, `expense_report_lines.acted_by_email`). 화면에는 보이지 않지만, 분쟁 시 실제 조작 계정을 추적할 수 있다.

직원 9명 규모에서 서로를 신뢰하는 조직이라는 전제 위의 결정이다. 나중에 계정 연결을 정비하면 로그인 기반으로 되돌릴 수 있도록, 행위자 판정은 `resolveActor()` 한 곳에 모아둔다.

### 왜 전결·대결·전단계 반려를 넣지 않는가

셋 다 결재자가 2명 이상일 때만 의미가 있다. 실사용 결재선은 전부 1단계였다. 대결은 대리결재자·위임기간·위임사유를 등록하는 별도 화면까지 필요하다. 결재자가 여러 단계로 늘어나면 그때 추가한다.

## 화면 구조

경로는 `/approval`. 좌측 문서함 사이드 + 우측 목록/상세.

```
기안함      저장된 / 상신한 / 회수된 / 반려된 / 완료된
결재함      결재전 / 진행중 / 반려된 / 완료된
문서대장    완료 문서 전체
```

카카오워크의 수신함·공람함·참조함·부서문서함은 만들지 않는다. 역할을 결재자+협조자 2종으로 정했으므로 채울 문서가 없다.

목록 컬럼: 문서번호 / 기안제목 / 기안자 / 지급총계 / 상신일시 / 상태
문서대장 검색 조건: 상신일 범위 / 기안제목 / 기안자

### 기안 작성 화면

카카오워크 배치를 그대로 따른다.

```
[기안 문서 정보]  기안양식(지출결의서) | 문서번호(완료 전 "-") | 보존연한 5년 | 기안자 | 기안부서
[결재선]          기안 카드 + [결재선 설정] 버튼
[안내]            "결제 관련 지출결의서 입니다."
[기안내용]
   기안제목 *              50자
   파일첨부                20MB 미만, 이미지/문서, 최대 10개
   참조문서                다른 결의서 링크
   ─────────────────────────────
   [엑셀 업로드] + 양식 다운로드 링크
   지급 총계(원)           읽기전용, 지급정보 합계 자동계산
   지급 정보  [추가]
      거래처명* | 지급금액* | 지급요청일* | 은행* | 계좌번호* | 사업자등록번호 | 삭제
   상세 내용  [추가] [일괄 적용]
      □ | 거래처명(지급정보에서 선택) | 계정 | 내용 | 부서명 | 금액 | 비고 | 삭제
   본문 에디터            기본값 "※ 첨부 파일에 견적서, 세금계산서 첨부할 것!!"
[하단]            [임시저장] [상신하기]
```

`상세 내용`의 첫 행은 카카오워크와 동일하게 **일괄 적용용 템플릿 행**이며 저장되지 않는다. 첫 행에 값을 넣고 대상 행을 체크한 뒤 `[일괄 적용]`을 누르면 동일하게 채워진다.

**카카오워크와 유일하게 다른 점**: 상단 `공개여부`(공개/부서공개/비공개) 필수 선택 칸을 뺀다. 부서가 하나뿐이라 구분할 대상이 없고, 확인한 문서 3건도 전부 `공개`였다. 되살리려면 `expense_reports`에 `visibility` 컬럼과 상단 셀렉트만 추가하면 된다.

### 결재선 설정 팝업

```
┌ 좌: 직원 검색 + 목록 ┐  ┌ 중앙 ┐  ┌ 우: 결재선 ─────────┐
│ 이름/ID 검색         │  │[결재]│  │ 기안  김태정         │
│ 고성준 / 조혜진 /    │  │[협조]│  │ ───────────────────  │
│ 김태정 / 김덕민 /    │  └──────┘  │ 결재/협조 (순서 변경) │
│ 김현준 / 송승란 /    │            └──────────────────────┘
│ 최원혁 / 김재호      │              [취소]  [적용]
└──────────────────────┘
```

- 기본 결재선 없음 — 매번 직접 지정한다
- 기안자는 본인을 결재자로 지정할 수 없다
- 아래로 갈수록 상위 결재자 (카카오워크와 동일)
- **마지막 사람은 반드시 `결재` 역할**이어야 한다. 협조자로 끝나는 결재선은 저장을 막는다

## 상태 전이

```
        [임시저장]
            ↓
        ┌ 저장된 ┐ ──삭제──> 소멸
        └───┬────┘
          상신
            ↓
      ┌─ 진행중 ─┐
      │          ├── 회수 ──> 회수된 ──재상신──┐
   승인│          ├── 반려 ──> 반려된 ──재상신──┤──> 진행중
      │          │              └──삭제──> 소멸 │
      ↓          └── 결재취소 ──> 이전 차례로 ──┘
   ┌ 완료 ┐  ← 문서번호 채번 + expenses 생성
   └──┬───┘
     재기안 ──> 새 저장된 문서
```

`status` 값: `draft`(저장된) / `pending`(진행중) / `approved`(완료) / `rejected`(반려된) / `withdrawn`(회수된)

| 액션 | 주체 | 조건 | 결과 |
|---|---|---|---|
| 임시저장 | 기안자 | — | `draft` |
| 상신 | 기안자 | `draft`·`withdrawn`·`rejected` | `pending`, `submitted_at` 기록, 1차 결재자에게 알림 |
| 회수 | 기안자 | `pending` **이고 1차 결재자가 아직 미처리** | `withdrawn` |
| 삭제 | 기안자 | `draft`·`withdrawn`·`rejected`만 | 문서 삭제. 진행중·완료는 삭제 불가 |
| 재상신 | 기안자 | `withdrawn`·`rejected` | 내용과 결재선을 수정한 뒤 `pending`. 기존 결재 이력(누가 언제 무슨 의견으로 반려했는지)은 지우지 않고 남기며, 결재선 `state`만 `waiting`으로 되돌린다 |
| 승인 | **현재 차례인 결재자만** | — | 다음 차례로 이동. 마지막이면 `approved` + 채번 + `expenses` 생성 |
| 반려 | 현재 차례인 결재자만 | 의견 필수 | `rejected`, 기안자에게 알림 |
| 결재취소 | 승인했던 결재자 | 다음 결재자가 미처리 **이고 문서가 `approved`가 아닐 때** | 본인 `state`를 `waiting`으로 되돌리고 차례 복귀 |
| 재기안 | 누구나 | `approved` 문서 | 내용·지급정보·상세내용을 복제한 새 `draft` 생성. 결재선과 첨부는 복제하지 않는다 |

`approved` 이후 결재취소를 막는 이유: 이미 `expenses` 레코드가 생성되고 실제 송금이 나간 상태다. 잘못 승인했다면 지출관리에서 직접 정정한다.

| `vendor_name` | text not null | 거래처명 (자유 텍스트) |
| `amount` | numeric not null | 지급금액 |
| `pay_request_date` | date not null | 지급요청일 |
| `bank` | text not null | 은행 |
| `account_no` | text not null | 계좌번호 |
| `business_no` | text | 사업자등록번호 |
| `expense_id` | uuid → expenses | 승인 시 생성된 지출. **중복 생성 방지 키** |

### `expense_report_details` — 상세 내용

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` / `report_id` / `seq` | | cascade 삭제 |
| `vendor_name` | text | 지급정보 거래처 중 선택 |
| `account` | text | 계정 |
| `content` | text | 내용 |
| `dept_name` | text | 부서명 |
| `amount` | numeric | 금액 |
| `note` | text | 비고 |

### `expense_report_lines` — 결재선

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` / `report_id` | | cascade 삭제 |
| `seq` | int | 결재 순서. 작을수록 먼저 |
| `staff_id` | uuid → staff | |
| `role` | text | `approval`(결재) / `cooperation`(협조) |
| `state` | text | `waiting` / `approved` / `rejected` |
| `acted_at` | timestamptz | 처리 일시 |
| `comment` | text | 결재의견 |

"현재 차례"는 `state = 'waiting'`인 행 중 `seq`가 가장 작은 행이다. 결재취소는 본인 행을 `waiting`으로 되돌리므로 별도 상태값을 쓰지 않는다.

**협조자는 결재자와 동일하게 동작한다.** 자기 차례가 되면 승인/반려를 하고, 처리하기 전까지 다음 사람으로 넘어가지 않는다. 두 역할의 차이는 결재선 카드에 `결재`로 표시되느냐 `협조`로 표시되느냐, 그리고 **마지막 자리에 올 수 있느냐**뿐이다.

### `expense_report_files` — 첨부

`id` / `report_id`(cascade) / `file_name` / `file_url` / `size` / `uploaded_at`

Supabase Storage에 올리고 기존 `/api/storage/upload`·`/api/storage/delete`를 재사용한다. 제한은 카카오워크와 동일하게 20MB 미만, 이미지(jpg·jpeg·png·gif)와 문서(doc·docx·ppt·pptx·xls·xlsx·pdf·hwp), 최대 10개.

### `expense_report_refs` — 참조문서

`id` / `report_id`(cascade) / `ref_report_id` → expense_reports

### `doc_sequences` — 문서번호 채번

| 컬럼 | 설명 |
|---|---|
| `form_abbr` | `CDV` |
| `year` | 2026 |
| `last_no` | 순번. **2026년은 `157`로 시드**해서 카카오워크 다음 번호부터 이어간다 |

pk는 `(form_abbr, year)`. 서버 API에서 `UPDATE ... SET last_no = last_no + 1 RETURNING last_no`로 원자적으로 증가시켜 번호 중복을 막는다.

### `push_subscriptions` — 앱푸시 기기

`id` / `staff_id` → staff / `endpoint` unique / `p256dh` / `auth` / `user_agent` / `created_at`

한 직원이 여러 기기를 쓸 수 있으므로 `staff_id`는 unique가 아니다.

### RLS

기존 테이블들과 동일하게 운영 RLS는 켜지 않는다(프론트가 anon으로 직접 읽는 구조와 맞춘다). 쓰기 보호는 아래 API 계층에서 한다.

## API 라우트

조회는 프론트에서 Supabase 직접. **아래 액션은 전부 서버 라우트로만** 처리한다.

| 경로 | 역할 |
|---|---|
| `POST /api/approval/save` | 임시저장 / 기안 수정 / 재기안 문서 생성 |
| `POST /api/approval/delete` | 삭제 |
| `POST /api/approval/submit` | 상신 |
| `POST /api/approval/withdraw` | 회수 |
| `POST /api/approval/approve` | 승인 (최종 승인이면 채번 + expenses 생성) |
| `POST /api/approval/reject` | 반려 |
| `POST /api/approval/cancel` | 결재취소 |
| `POST /api/approval/excel-parse` | 엑셀 업로드 파싱 |
| `GET /api/approval/excel-template` | 엑셀 양식 다운로드 |
| `POST /api/push/subscribe` | 푸시 구독 등록 |
| `POST /api/push/send` | 푸시 발송 (내부 호출 전용) |

모든 액션 라우트의 공통 절차:

1. `getAuthUser()`로 로그인 사용자 확인 (없으면 401)
2. `user.email` → `staff.email`로 직원 특정 (없으면 403)
3. 문서 상태와 결재선을 다시 읽어 **그 직원이 실제로 이 액션을 할 자격이 있는지 검증**
   - 승인·반려·취소: 현재 차례가 본인인가
   - 저장·상신·회수·삭제: 본인이 기안자인가 (신규 저장·재기안은 기안자를 로그인 사용자로 강제한다)
4. `service_role` 클라이언트로 쓰기

클라이언트가 보낸 `staff_id`는 절대 신뢰하지 않는다.

## 승인 → 지출 자동등록

최종 승인 트랜잭션 안에서 **지급정보 1행당 `expenses` 1건**을 만든다.

| `expenses` 컬럼 | 값 |
|---|---|
| `amount` | `payments.amount` |
| `expense_date` | `payments.pay_request_date` |
| `category` | 최종 결재자가 승인 팝업에서 고른 계정과목 |
| `title` | 기안제목. 지급정보가 2행 이상이면 `기안제목 (거래처명)` |
| `staff_id` | 기안자 |
| `receipt_url` | 첨부파일 첫 번째의 `file_url` |
| `memo` | `[CDV-26-000158] 거래처명 / 은행 계좌번호` |
| `site_id` | `null` — 양식에 현장 칸이 없다 |

생성된 `expenses.id`를 `expense_report_payments.expense_id`에 되기록한다. **이미 값이 있는 행은 건너뛴다** — 재처리나 중복 호출로 지출이 두 번 생기는 것을 막는 유일한 방어선이다.

계정과목 후보는 기존 `/expenses`의 `EXPENSE_CATS`를 그대로 쓴다: 식대 / 교통비 / 자재비 / 현장경비 / 노무비 / 사무용품 / 기타.

승인 팝업 구성: `승인 / 반려` 선택 → **승인일 때만** 계정과목 드롭다운 표시(최종 결재자에게만) → 결재의견 입력 → `[결재]`.

### 앱푸시 (Web Push)

수신 쪽은 이미 완성돼 있다. `public/sw.js:37`에 `push` 이벤트 핸들러가 있고 `notificationclick`에서 payload의 `url`로 이동한다. 새로 만들 것은 보내는 쪽이다.

1. VAPID 키 발급 → `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` 환경변수
2. `web-push` 패키지 추가
3. `push_subscriptions` 테이블 + `/api/push/subscribe`
4. 설정 화면에 "알림 켜기" 토글 (`Notification.requestPermission()` → `pushManager.subscribe()` → 서버 등록)
5. 발송 시 payload에 `url: /approval/{id}`를 넣어 알림을 누르면 해당 문서로 바로 들어가게 한다
6. 발송이 `410 Gone`을 반환하면 만료된 구독이므로 `push_subscriptions`에서 삭제한다

**iOS 제약**: 사파리 탭에서는 푸시가 오지 않고 홈 화면에 추가한 PWA에서만 온다(iOS 16.4+). 설정 화면의 알림 토글 아래에 안내 문구를 넣는다.

### 화면 배지

- 사이드바 `결재전` 옆 미처리 건수
- 대시보드에 `결재할 문서 N건` 카드 (누르면 `/approval` 결재전으로 이동)

## 엑셀 업로드

카카오워크와 동일하게 양식 다운로드 → 작성 → 업로드로 지급정보·상세내용 행을 일괄 채운다. 단일 기능 중 작업량이 가장 크다.

- `GET /api/approval/excel-template` — 지급정보 시트와 상세내용 시트를 가진 xlsx를 생성해 내려준다
- `POST /api/approval/excel-parse` — 업로드된 xlsx를 파싱해 행 배열을 반환한다. **DB에 바로 쓰지 않고 화면의 표에 채워 넣기만 한다.** 사용자가 확인·수정한 뒤 임시저장/상신한다
- 파싱 실패한 행은 버리지 않고 어느 행이 왜 실패했는지 함께 반환해 화면에 표시한다 (금액이 숫자가 아님, 날짜 형식 불일치, 필수값 누락)
- 날짜는 기존 `validateProjectData()` 규칙과 맞춰 `YYYY-MM-DD`로만 정규화한다

## 코드 구조

프로젝트 관례(`src/components/[기능명]/[기능명]Page.tsx` + `src/app/[기능명]/page.tsx`)를 따르되, `/expenses`가 단일 파일 1019줄로 커진 전례가 있으므로 처음부터 나눈다.

  ApprovalLineView.tsx                   결재선 카드 표시 (상세/목록 공용)

상태 전이 규칙(`status.ts`)은 화면과 API 라우트가 **같은 함수를 공유**한다. 버튼 노출 조건과 서버 검증이 갈라지면 화면엔 없는 버튼을 API로 호출하는 구멍이 생긴다.

UI는 기존 규칙을 따른다 — 인라인 편집, 드래그앤드롭 첨부, Lucide 아이콘 단색, 이모지 금지.

## 열린 항목

- **과거 876건 이관**: 이번 범위 밖이다. 카카오워크는 관리자 백업으로 `워크스페이스명/양식명/기안년도/기안월/문서번호` 폴더 구조의 zip을 받을 수 있다(신청 익일 처리, 다운로드 7일). 이관이 필요해지면 별도 과제로 잡는다.
- **현장별 지출 집계**: 지급정보에 `site_id`를 추가하는 후속 작업으로 열어둔다.
- **공개여부 칸**: 뺐다. 되살리려면 `expense_reports.visibility` 컬럼과 상단 셀렉트만 추가하면 된다.
