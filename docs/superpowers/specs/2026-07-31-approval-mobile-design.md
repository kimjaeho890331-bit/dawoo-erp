# 지출결의서 결재 화면 모바일 설계

작성 2026-07-31.

## 왜 하는가

`/approval` 계열 화면 11개 파일에 반응형 클래스가 **하나도 없다.** 데스크톱만 보고 만들었다.
실제 폰에서 열어보니 목록 화면의 글자가 한 자씩 세로로 떨어졌다.

원인은 두 겹이다.

1. `ApprovalPage`가 자체 사이드바 `w-48`(192px)을 고정으로 깔고 있다.
2. 그 옆의 목록이 `table-fixed` 6칸이다.

390px 폰에서 사이드바가 192px을 먹으면 표에 190px이 남고, 그것을 6칸으로 나누면 한 칸이 30px이다.
`table-fixed`는 칸 폭을 줄이지 않고 글자를 세로로 접는다.

결재는 이동 중에 처리하는 일이 많다. 웹푸시 알림을 붙여놨으므로 폰에서 알림을 받고 그 자리에서
열어보게 된다. 그때 이 화면이 나오면 알림이 무의미해진다.

## 범위

기안 작성까지 전부 모바일 최적화한다. 데스크톱은 건드리지 않는다.

| 화면 | 파일 | 모바일에서 바뀌는 것 |
|---|---|---|
| 목록 | `ApprovalPage.tsx` | 사이드바 제거, 문서함 드롭다운, 행→카드 |
| 문서 상세 | `ApprovalDetail.tsx` | 표 4개를 세로로 해체, 액션 하단 고정 |
| 기안 작성 | `DraftForm.tsx` | 5단계 마법사 |
| 지급정보 입력 | `PaymentTable.tsx` | 건별 카드 편집 |
| 상세내용 입력 | `DetailTable.tsx` | 건별 카드 편집 |
| 결재선 설정 | `ApprovalLineModal.tsx` | 하단 시트 |
| 승인/반려 | `ApproveModal.tsx` | 하단 시트 |

## 기본 결정

### 분기점은 768px (Tailwind `md`)

`md` 미만이 모바일이다. 태블릿 세로(768px)는 데스크톱 취급한다.
결재는 사무실 PC 아니면 폰이고 태블릿을 쓰는 사람이 없다.

### 표를 카드로 바꾸는 데는 마크업 두 벌을 쓴다

CSS만으로 6칸 표를 카드로 만들 수 없다. 구조가 다르다.
`hidden md:block` / `md:hidden`으로 갈라서 화면 폭에 따라 하나만 렌더한다.

**대가**: 목록과 상세의 *표시* 마크업이 두 벌이 된다. 칸을 하나 추가하면 두 곳을 고쳐야 한다.

**그럼에도 이 방식인 이유**: 사용자가 "컴퓨터는 안 해도 된다"고 명시했다. 데스크톱 마크업을
그대로 두면 데스크톱이 깨질 확률이 0이다. 하나의 마크업을 반응형으로 개조하면 데스크톱도
같이 바뀌고, 지금 실제로 쓰고 있는 화면을 위험에 빠뜨린다.

**갈라지지 않는 것**: 데이터 조회, `currentTurnLine` 같은 판정, 저장·상신 같은 동작은 전부
한 벌로 공유한다. 갈라지는 것은 "보여주는 모양"뿐이다.

### 기안 작성은 5단계 마법사

사용자 선택이다. 한 화면 스크롤과 비교해서 고른 것이다.

`제목·기안자` → `지급정보` → `상세내용` → `첨부·참조` → `결재선` → `확인`

단계별의 약점은 중간 수정이 번거롭다는 것이다. 이를 **확인 단계**로 보완한다. 마지막에 입력한
내용을 전부 보여주고, 항목마다 `수정`을 누르면 해당 단계로 점프한다. 상신은 확인 단계에서만 한다.

임시저장은 모든 단계에서 가능하다. 폰 작업은 중간에 끊기기 쉽다.

### 액션 버튼은 하단 고정

사용자 선택이다. 문서가 길어도 승인·반려가 항상 엄지에 닿는다.

대가: 내용을 끝까지 안 보고 승인할 수 있다. 사용자가 이 위험을 알고 선택했다.

`position: fixed` + `padding-bottom: env(safe-area-inset-bottom)`으로 아이폰 홈바를 피한다.
고정 바 높이만큼 본문 아래에 여백을 줘서 마지막 내용이 가리지 않게 한다.

## 화면별 설계

### 목록

모바일에서 `aside`를 `hidden md:flex`로 숨긴다. 대신 본문 위에 둘을 놓는다.

1. **현재 직원** — 기존 `ActorPicker` 재사용
2. **문서함 드롭다운** — 옆에 결재전 건수 배지

문서함을 가로 스크롤 칩으로 하지 않은 이유: 기안함에도 "반려된·완료된"이 있고 결재함에도
같은 이름이 있다. 칩으로 늘어놓으면 어느 쪽인지 구분되지 않는다. 드롭다운이면
`기안함 · 반려된` / `결재함 · 반려된`으로 그룹을 함께 보여줄 수 있다.

목록 한 건은 카드다.

```
[제목 (최대 2줄)]              [상태 배지]
[금액 — 크게]
[기안자 · 상신일시 — 작게]
```

문서번호는 카드에서 뺀다. `CDV-26-000158`이 폰에서 폭을 크게 먹는데, 목록에서 문서번호로
찾는 일이 드물다. 상세 화면에는 그대로 있다.

카드 전체가 탭 영역이다. 제목만 링크였던 데스크톱과 다르다.

### 문서 상세

- **기안정보** — 2열 표를 `라벨 / 값` 세로 나열로
- **지급정보** — 건별 카드. 거래처명과 금액이 위, 은행·계좌·사업자번호가 아래
- **상세내용** — 같은 형태의 카드
- **결재선** — 세로 단계 목록. 상태 아이콘 + 이름 + 구분 + 일시
- **첨부·참조** — 이미 세로라 폰트와 탭 영역만 키운다
- **액션** — 하단 고정 바

### 기안 작성

단계 상태는 `DraftForm` 안의 `step` 하나로 관리한다. 데이터 상태(`payments`, `details`,
`files`, `lines`)는 지금 구조를 그대로 쓴다. 단계는 *보여줄 것을 고르는 필터*일 뿐이고
데이터 모델을 바꾸지 않는다.

데스크톱은 `step`을 무시하고 전부 한 화면에 그린다.

**단계 이동 시 검증**: 다음으로 넘어갈 때 그 단계의 필수값만 확인한다. 마지막 확인 단계에서
전체를 다시 확인한다. 중간에 비어 있어도 임시저장은 된다.

### 지급정보 카드 편집

한 건이 카드 한 장이다.

```
1번째 지급 건                    [삭제]
[거래처명            🔍]   ← VendorNameCell 재사용
[지급금액                  ]
[은행    ] [계좌번호        ]
[지급요청일                ]
[사업자번호                ]
```

거래처 자동입력을 그대로 살린다. 폰에서 계좌번호를 손으로 치는 것이 특히 괴로우므로
데스크톱보다 오히려 더 중요하다.

`VendorNameCell`의 후보 목록은 `document.body` 포탈에 `position: fixed`로 뜬다. 폰에서는
입력창 아래 공간이 부족할 수 있으므로, 아래 공간이 목록 높이보다 작으면 위로 띄운다.

### 팝업 두 개

`ApprovalLineModal`, `ApproveModal`을 모바일에서 하단 시트로 바꾼다.
`max-h-[85dvh]` + 내부 스크롤. `dvh`를 쓰는 이유는 모바일 브라우저 주소창이 접혔다 펴지면서
`vh`가 튀기 때문이다.

## 공통 규칙

### 입력창 글자 16px

아이폰 사파리는 글자가 16px보다 작은 입력창을 누르면 화면을 자동 확대한다. 지금 결재 화면
입력창이 전부 `text-xs`(12px)라서 기안 작성 내내 화면이 들썩인다.

모바일에서 `text-base`(16px), 데스크톱에서 `md:text-xs`로 되돌린다.

### 탭 영역 44px

행 삭제 아이콘이 13px이다. 아이콘 크기는 두더라도 누를 수 있는 영역을 44px 이상으로 잡는다.

### 색은 디자인 토큰만

기존 규칙 그대로. 하드코딩 색을 쓰지 않는다.

## 검증

이 프로젝트의 Vitest는 순수 로직만 다룬다. 화면 테스트가 없다.

따라서 검증은 실제 브라우저에서 한다.
- 개발 서버를 `SKIP_AUTH=1`로 띄운다 (미들웨어가 개발 환경에서만 인증을 건너뛴다)
- 뷰포트 375px로 목록·상세·기안 작성을 확인한다
- 콘솔 에러가 없는지 본다
- 데스크톱 폭(1280px)에서 화면이 이전과 같은지 확인한다 — 이것이 가장 중요하다

## 하지 않는 것

- 데스크톱 화면 변경
- 결재 로직·데이터 모델 변경
- 하단 탭바 같은 앱 전역 내비게이션 개편 (`ClientLayout`은 이미 모바일 대응이 되어 있다)
- 목록 검색·필터 추가 (별개 과제)
