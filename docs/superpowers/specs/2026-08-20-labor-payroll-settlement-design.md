# 일용직 근무관리 — 노무사 왕복 연동 설계

작성일: 2026-08-20

## 배경

일용직 노무비는 현장별로 다음 순환을 돈다.

1. 현장 × 공종 × 월 단위로 노무비 엑셀을 만든다. 1번 시트는 근무명세, 2번 시트는 근무자별 신분증·건설업기초안전보건교육이수증·통장사본 이미지다.
2. 노무사에게 보낸다.
3. 노무사가 공제액을 책정해 `_공제액산정` 파일로 회신한다. 빈칸으로 보낸 국민연금·건강보험·장기요양을 채우는 것이 기본이지만, 나이·외국인 여부·공수에 따라 갑근세를 포함한 6종 전부가 바뀌어 오기도 한다.
4. **회신본 금액이 확정 금액이다.** 우리가 계산해 보낸 값은 신청 근거일 뿐이다.

지금은 전 과정이 수기다. 2번 시트 이미지는 매달 사람이 찾아 붙이고, 회신본은 NAS 폴더에만 쌓여 ERP에서 조회되지 않는다.

기준 자료: `\\Dawoo-server\입찰사업\※ 입찰계약 완료\입찰 준공 91. (군수-전체-2) 00부대 병영생활관 보수공사\11. 노무비\12월\미장\` 의 발송본·회신본 2종.

## 현행 파악

### 현장 파일 구조

**1번 시트(근무명세)** — 근무자 1명이 2행을 쓴다. 윗행이 1~15일, 아랫행이 16~31일.

| 열 | 내용 | 비고 |
|---|---|---|
| B | no | |
| C | 성명 | |
| D | 주민등록번호 | |
| E~T | 일자별 출역 | 근무일에 `1` |
| U | 윗행=일수(`=SUM(E5:T6)`), 아랫행=일급 | |
| V | 노무비 총액(`=U5*U6`) | |
| W | 차량유지비 | |
| X~AC | 공제 6종 | 갑근세·주민세·고용보험·국민연금·건강보험·장기요양 |
| AD | 공제 합계 | |
| AE | 차감지급액 | |
| AF~AJ | 지급일·현장명·은행/계좌·연락처·공종 | 은행과 계좌는 `국민은행\n090-21-0802-997` 형태 한 칸 |

3행에 요율이 숫자로 박혀 있다(갑근세 0.027, 주민세 0.1, 고용보험 0.009, 국민연금 0.045, 건강보험 0.0343, 장기요양 0.1152).

갑근세·주민세·고용보험은 수식으로 자동 산출된다. **국민연금(AA)·건강보험(AB)·장기요양(AC)이 빈칸으로 나가고 노무사가 이를 채워 보낸다.** 다만 회신 시 우리가 계산해 보낸 나머지 3종도 함께 조정될 수 있다(4-3).

**2번 시트(신분증, 통장사본)** — 3열 구성(신분증 / 건설업기초안전보건교육이수증 / 통장사본). 근무자 1명이 8행 1블록을 쓰고 3행부터 시작한다(3·11·19·27·35·43·51). 원본은 7명분 슬롯이 병합돼 있고 그 안에 이미지가 앵커링돼 있다. **근무자 이름 표기가 없어 1번 시트 행 순서와의 암묵적 일치에 의존한다.**

### 발송본과 회신본 비교

전 시트를 셀 단위로 대조한 결과, 이번 달 회신본은 공제액 입력이 없었고(해당 근무자 2일 근무로 4대보험 미해당) **소계 수식 범위만 한 칸씩 밀려 있었다.**

```
발송본 X13 =SUM(X5:X12)   →   회신본 X13 =SUM(X5:Y12)
```

X13부터 AE13까지 8개 칸 전부 같은 방향으로 밀렸다. 회신본 소계는 옆 열까지 함께 더하고 있어 **현재 회신본의 소계 행은 신뢰할 수 없다.** 설계에 이 사실을 반영한다(아래 4-3).

### ERP 현황

- `labor_records` 테이블과 [LaborPage](../../../src/components/labor/LaborPage.tsx)가 이미 있다. 월별 그리드, 요율 편집, 자동저장이 동작한다.
- [/api/labor/export](../../../src/app/api/labor/export/route.ts)가 ExcelJS로 **1번 시트를 이미 재현한다.** 열 배치와 수식이 현장 원본과 사실상 같다.
- `vendors` 테이블에 `vendor_type = '일용직'` 과 `id_card_url` · `bankbook_url` · `safety_cert_url` 3개 필드가 이미 있다([VendorsPage](../../../src/components/vendors/VendorsPage.tsx)).

**빠진 연결고리**

- 노무비 근무자는 과거 `labor_records`에서 이름만 자동완성할 뿐 거래처DB와 연결이 없다. 이미지를 이름으로 끌어올 근거가 없다.
- 2번 시트를 만드는 기능이 없다.
- 회신본을 읽거나 보관하는 기능이 없다.
- `vendors`에 주민등록번호 칸이 없어 매달 노무비 화면에서 직접 친다.

## 범위

**한다**

- 거래처DB 일용직과 노무비 근무자 연결
- 현장 × 공종 × 월 단위 발송본 생성(1번 시트 + 2번 시트 이미지 자동 삽입)
- 노무사 회신본 보관과 목록 관리
- 회신본 공제액을 미리보기 확인 후 반영, 확정 금액 추적

**안 한다**

- NAS 자동 저장 — 다운로드까지만 담당한다. NAS 연동은 별건 과제로 남아 있다.
- 메일 발송 — 담당자가 직접 보낸다.
- PDF → 이미지 변환 — PDF 서류는 빈칸으로 두고 경고한다.
- RLS 정비 — 신규 테이블도 현행 관례(RLS 미적용)를 따른다. 사유는 6절.

## 설계

### 1. 데이터 모델

#### 1-1. `vendors` — 주민등록번호 추가

```sql
ALTER TABLE vendors ADD COLUMN IF NOT EXISTS resident_id TEXT;
```

일용직 전용 필드다. 거래처(협력업체)에는 쓰지 않는다. 같은 레코드에 이미 신분증 사본을 보관하고 있어 민감도 수준이 달라지지 않고, 매달 오타 날 자리가 하나 없어진다. 거래처DB 일용직 수정란에 입력칸을 추가한다.

#### 1-2. `labor_records` — 연결 컬럼 2개

```sql
ALTER TABLE labor_records ADD COLUMN IF NOT EXISTS vendor_id UUID REFERENCES vendors(id);
ALTER TABLE labor_records ADD COLUMN IF NOT EXISTS settlement_id UUID REFERENCES labor_settlements(id);
CREATE INDEX IF NOT EXISTS idx_labor_records_vendor ON labor_records(vendor_id);
CREATE INDEX IF NOT EXISTS idx_labor_records_settlement ON labor_records(settlement_id);
```

`settlement_id`가 `labor_settlements`를 참조하므로 **마이그레이션에서는 1-3의 `CREATE TABLE`이 먼저 와야 한다.** 문서는 읽기 순서상 이 절을 앞에 두었을 뿐이다.

- `vendor_id` — 거래처DB 일용직 참조. 2번 시트 이미지를 끌어오는 근거.
- `settlement_id` — 이 행의 공제액이 어느 회신본에서 왔는지. 값이 있으면 **확정**, 없으면 **예상**이다.

#### 1-3. `labor_settlements` — 회신본 보관 (신규)

회신 파일 1건이 1행이다. 파일 하나가 여러 근무자를 포괄하므로 `labor_records`에 파일을 붙이면 1:N이 맞지 않는다.

```sql
CREATE TABLE IF NOT EXISTS labor_settlements (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  year INT NOT NULL,                  -- 귀속 연도
  month INT NOT NULL,                 -- 귀속 월
  site_name TEXT,                     -- 현장명
  work_type TEXT,                     -- 공종
  rep_worker_name TEXT,               -- 대표 근무자 이름 (파일명의 "(고영도)")
  received_date DATE,                 -- 노무사 회신일
  file_name TEXT NOT NULL,            -- 원본 파일명 (한글 그대로)
  file_url TEXT NOT NULL,             -- 내려받기 URL
  file_path TEXT NOT NULL,            -- 저장소 키 (삭제용)
  worker_count INT,                   -- 파싱 요약: 인원
  total_deduction BIGINT,             -- 파싱 요약: 공제 합계
  total_net BIGINT,                   -- 파싱 요약: 실지급 합계
  applied_at TIMESTAMPTZ,             -- 공제액 반영 시각 (NULL이면 미반영)
  note TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_labor_settlements_period ON labor_settlements(year, month);
CREATE INDEX IF NOT EXISTS idx_labor_settlements_received ON labor_settlements(received_date DESC);
```

**저장 경로가 폴더 구조가 될 수 없다.** [safeStoragePath](../../../src/lib/utils/storagePath.ts)가 한글을 밑줄로 치환한다 — Supabase Storage가 한글 키를 `InvalidKey`로 거부하기 때문이다. `(군수-전체-2)00부대현장`을 폴더명으로 쓰면 `_______`이 되고 현장이 다른 파일끼리 경로가 충돌한다.

따라서 **파일은 충돌 없는 키로 저장하고, 분류는 전부 DB 컬럼이 담는다.**

```
labor/{year}-{month}/{타임스탬프}_{정리된파일명}.xlsx
```

원본 파일명은 `file_name`에 한글 그대로 보존해 목록과 내려받기에 쓴다. 기존 결재 첨부가 쓰는 방식과 같다.

**재발송 대응** — 같은 현장·공종·월에 수정본이 오면 새 행으로 쌓는다. `received_date` 최신 건이 유효하고, 이전 회신본도 목록에 남아 무엇이 언제 바뀌었는지 보인다.

### 2. 근무자 ↔ 거래처DB 연결

노무비 화면에서 근무자를 고르는 방식을 **거래처DB 일용직 목록 선택**으로 바꾼다. 고르면 주민번호·연락처·은행·계좌가 함께 채워지고 `vendor_id`가 박힌다. 목록에 없는 사람은 그 자리에서 일용직 신규 등록 후 바로 연결한다.

**기존 데이터 자동 연결 규칙**

1. 이름이 정확히 일치하는 일용직이 한 명이면 연결한다.
2. 둘 이상이면 **연락처로 판정한다.** `labor_records.phone`과 `vendors.phone`이 일치하는 한 명이 있으면 그 사람으로 연결한다.
3. 연락처로도 못 가리면 연결하지 않고 화면에 "미연결"로 표시한다. 담당자가 직접 고른다.

번호는 하이픈·공백을 제거해 숫자만으로 비교한다(`010-1234-5678`과 `01012345678`이 같아야 한다).

`vendor_id`가 없으면 2번 시트 이미지를 가져올 수 없으므로 엑셀 생성 시 경고 목록에 오른다.

### 3. 발송본 생성

`/api/labor/export`를 확장한다. 요청에 **현장 × 공종 × 월**을 받아 해당 근무자만 담는다.

현장·공종을 지정하지 않으면 지금처럼 그달 전체를 담고 2번 시트를 만들지 않는다. 기존 `내보내기` 버튼이 그대로 동작해야 하기 때문이다.

파일명은 현장 파일 규칙을 따른다.

```
25년 12월 _(군수-전체-2)00부대현장(고영도).xlsx
```

`(고영도)`는 대표 근무자 — 그 파일에서 `sort_order`가 가장 앞선 근무자의 이름이다.

#### 3-1. 1번 시트

기존 생성 로직을 유지하고 대상 근무자만 걸러낸다. 수식·열 배치·요율 행은 그대로다.

#### 3-2. 2번 시트 (신규)

원본 레이아웃을 그대로 재현하되 두 가지를 더한다. 견본 파일로 확인받은 형태다.

- **A열에 근무자 이름을 넣는다.** 원본에는 없다. 지금은 1번 시트 행 순서와 2번 시트 블록 순서가 같다는 암묵적 약속뿐이라 인원이 늘면 누구 서류인지 확인할 방법이 없다. A열만 넓혀 쓰므로 나머지 칸 위치는 원본과 같다.
- **7명 제한을 없앤다.** 8행 1블록을 인원수만큼 늘린다(3·11·19·27…).

이미지는 `vendors`의 `id_card_url` · `safety_cert_url` · `bankbook_url`에서 가져와 병합 블록 정중앙에 비율을 유지해 배치한다. 블록 크기는 열 너비(B+C = 15.6+8.43자)와 행 높이(7행 × 20.1pt)에서 계산하고 여백 4px을 둔다.

**서류 예외**

| 상황 | 처리 |
|---|---|
| 이미지(jpg/png/webp 등) | 삽입 |
| PDF | 빈칸 + `(미등록)` 표시 + 경고 목록 |
| 미등록 | 빈칸 + `(미등록)` 표시 + 경고 목록 |
| 3개 모두 없음 | 블록은 그대로 두고 3칸 모두 표시 |

3개가 모두 없어도 블록을 유지한다. 근무명세에 이름이 있는데 서류 시트에서 통째로 빠지면 노무사가 누락을 알아채기 더 어렵다.

파일은 어떤 경우에도 생성된다. 응답에 누락 목록을 함께 실어 화면에 띄운다.

```
전상국 — 교육이수증 없음
임준영 — 신분증·교육이수증·통장사본 없음
```

### 4. 회신본 보관과 반영

#### 4-1. 업로드

일용직 근무관리 페이지의 **노무사 회신본** 탭에서 파일을 끌어다 놓는다. 서버가 파싱해 `year` · `month`(1번 시트 `E2` 기간) · `site_name`(`AG`열) · `rep_worker_name`(첫 근무자)을 자동으로 뽑고, `received_date`는 파일명 앞 `25.12.24` 패턴에서 읽되 없으면 업로드 시점 입력을 받는다. 공종은 화면에서 선택한 값을 쓴다.

자동 추출값은 전부 저장 전에 화면에서 수정할 수 있다.

업로드는 `/api/storage/upload`를 경유한다. 허용 경로 목록에 `labor/`를 추가해야 한다(xlsx 확장자와 20MB 제한은 이미 통과).

#### 4-2. 목록

기본 정렬은 회신일 최신순. 머리글을 눌러 **이름 · 날짜 · 현장명** 어느 쪽으로든 정렬된다. 검색은 세 항목 전부에 걸린다. 각 행에 요약(`8명 / 공제 1,234,560원`)과 반영 여부가 보이고, 원본 파일을 바로 내려받는다.

#### 4-3. 공제액 읽기

**열을 위치로 찾지 않는다.** 4행 머리글에서 `국민연금` · `건강보험` · `장기요양` 글자를 찾아 열을 정한다. 노무사가 열을 끼워 넣어 보내도 엉뚱한 칸을 읽지 않는다. 실제 회신본에서 소계 수식이 한 칸씩 밀려 온 전례가 있어 이 방어는 필수다.

**공제 6종을 전부 읽는다.** 갑근세·주민세·고용보험·국민연금·건강보험·장기요양 모두 회신본 값이 확정이다.

우리 요율 계산은 일괄 요율만 적용하므로 다음 경우에 실제와 어긋나고, 노무사는 이를 반영해 고쳐 보낸다.

- **나이** — 고령자는 국민연금이 빠지는 등 적용 대상이 달라진다
- **외국인** — 적용 보험과 요율이 내국인과 다르다
- **공수** — 하루가 1공수가 아니라 1.5공수면 일급 환산이 달라져 갑근세부터 바뀐다

따라서 우리 계산값은 어디까지나 **예상**이고, 회신본이 오면 6종 전부를 그 값으로 덮는다. 차감지급액도 덮은 값 기준으로 다시 계산한다.

**소계 행은 읽지 않는다.** 근무자 행의 값만 읽고 합계는 우리가 다시 계산한다.

실제 회신본에서 소계 8개 열이 모두 한 칸씩 밀려 있었다. 갑근세 소계에 주민세가 섞이고, 공제합계에 차감지급액이 섞여 40배가 되고, 차감지급액 소계에는 **지급일 날짜가 숫자로 더해졌다**(`624,150 + 46,017 = 670,167`, 46017은 2025-12-26의 엑셀 날짜값). 근무자가 한 명이고 4대보험이 0이라 세 열이 우연히 맞아 보였을 뿐, 인원이 늘면 전부 틀린다.

파일의 소계와 우리 계산이 다르면 미리보기에 경고로 표시하되, 근무자 행 기준으로 반영은 진행한다.

**일수·일급이 우리 기록과 다르면 경고한다.** 공수가 달라져 세액이 바뀐 경우 원인을 짚을 수 있어야 한다. 값 자체는 우리 기록을 유지하고 공제액만 덮는다.

수식으로 들어온 칸은 계산된 값(cached value)을 읽는다.

#### 4-4. 사람 맞추기

주민등록번호로 맞춘다. 이름은 동명이인과 오타가 있지만 주민번호는 유일하다. 주민번호가 비어 있으면 이름으로 맞추고, 그래도 애매하면 그 행을 "수동 확인"으로 남긴다.

#### 4-5. 미리보기 후 반영

업로드해도 자동 반영하지 않는다. 반영 대상을 표로 띄우고 확인을 받는다.

| 근무자 | 갑근세 | 주민세 | 고용보험 | 국민연금 | 건강보험 | 장기요양 | 상태 |
|---|---|---|---|---|---|---|---|
| 고영도 | 9,180 | 910 | 5,760 | – → 28,800 | – → 21,950 | – → 2,520 | 반영 |
| 전상국 | 12,400 → **0** | 1,240 → **0** | 4,500 | 15,000 → **0** | – | – | 반영 |
| 임준영 | — | — | — | — | — | — | 회신본에 없음 |

바뀌는 값은 굵게 표시한다. 위 표의 전상국은 고령·외국인처럼 적용이 달라져 우리 예상과 어긋난 경우를 보여준다.

파일에는 있는데 우리 쪽에 없는 사람, 우리 쪽에 있는데 파일에 없는 사람도 함께 뜬다. 일수·일급이 다르거나 소계가 맞지 않으면 경고 줄이 붙는다. 취소하면 아무것도 바뀌지 않는다.

확인하면 공제 6종(`ded_income_tax` · `ded_resident_tax` · `ded_employment` · `ded_pension` · `ded_health` · `ded_longterm`)을 덮고, 각 행의 `settlement_id`를 채우고, `labor_settlements.applied_at`을 기록한다.

#### 4-6. 확정 표시

`settlement_id`가 있는 행은 노무비 화면에서 **확정**으로 표시된다. 없으면 우리 계산값이므로 **예상**이다. 확정 표시를 누르면 근거가 된 회신본으로 이동한다.

### 5. 화면

일용직 근무관리 페이지에 탭을 둔다.

- **근무명세** — 기존 월별 그리드. 근무자 선택이 거래처DB 연동으로 바뀌고, 미연결·확정/예상 표시가 붙는다. 현장·공종 필터와 `내보내기` 버튼이 생긴다.
- **노무사 회신본** — 업로드, 목록, 미리보기 반영.

### 6. RLS

`labor_settlements`에 RLS를 켜지 않는다. 현행 프론트는 세션 없는 anon 클라이언트로 데이터를 읽기 때문에(`src/lib/supabase.ts`) authenticated 전용 정책을 켜면 화면이 빈다. `labor_records` · `labor_rates`가 같은 이유로 RLS 미적용이다.

`supabase/migrations/007_rls_all_tables.sql`이 전 테이블 일괄 적용을 준비해 두었으나 **아직 실행 전이고**, 실행 전에 `createBrowserClient` 전환이 선행돼야 한다. 그 정비가 끝나면 신규 테이블도 자동으로 포함된다(해당 마이그레이션이 public 스키마 전체를 순회한다).

## 구현 순서

세 덩어리로 나눈다. 각 단계가 끝나면 그 자체로 쓸 수 있다.

1. **연결 기반** — `vendors.resident_id`, `labor_records.vendor_id`, 거래처DB 주민번호 입력칸, 노무비 근무자 선택 연동, 기존 데이터 자동 연결. 이 단계만으로 매달 주민번호·계좌를 다시 치지 않아도 된다.
2. **발송본 생성** — export API 확장, 2번 시트와 이미지 삽입, 누락 경고. 1단계의 `vendor_id`에 의존한다.
3. **회신본 관리** — `labor_settlements`, 업로드·목록·파싱·미리보기 반영, 확정 표시. 1·2단계와 독립이지만 확정 표시가 `settlement_id`를 쓴다.

## 오류 처리

| 상황 | 처리 |
|---|---|
| 서류가 PDF이거나 미등록 | 빈칸 + 경고 목록. 파일은 생성 |
| 근무자가 거래처DB에 미연결 | 서류 3개 모두 빈칸 + 경고 목록 |
| 회신본에 공제 항목 머리글이 없음 | 파싱 중단, 사유 표시. 파일은 보관됨 |
| 회신본 근무자를 우리 기록에서 못 찾음 | 미리보기에 "회신본에만 있음"으로 표시, 반영에서 제외 |
| 회신본 소계와 우리 계산이 불일치 | 미리보기에 경고 표시, 반영은 진행 가능 |
| 회신본 일수·일급이 우리 기록과 다름 | 미리보기에 경고 표시. 공제액만 덮고 일수·일급은 우리 값 유지 |
| 업로드 실패(용량·형식) | 저장하지 않고 사유 표시 |

## 테스트

- 요율 계산: 일급 15만 이하 소액부징수, 10원 절사, 건강보험 기준 장기요양 산출
- 2번 시트: 1명 / 7명 / 12명에서 블록 위치가 3·11·19…로 맞는지, 이미지가 블록을 넘지 않는지
- 서류 예외: 이미지 없음 / PDF / 일부만 있음 3가지
- 근무자 자동 연결: 동명이인 2명 중 연락처로 판정, 하이픈 유무 차이
- 회신본 파싱: 열이 밀린 파일, 머리글이 없는 파일, 수식으로 들어온 값
- 공제 6종 덮어쓰기: 갑근세가 0으로 내려온 경우(고령·외국인), 우리 예상보다 커진 경우
- 소계 검증: 소계가 밀린 실제 회신본으로 경고가 뜨고 반영은 정상 진행되는지
- 사람 맞추기: 주민번호 일치, 주민번호 없이 이름만 일치, 양쪽 모두 애매

## 확인된 사항

두 건 모두 2026-08-20에 확인됐다.

- **노무사는 공제 6종을 모두 고쳐 보낸다.** 나이·외국인 여부·공수(1공수 vs 1.5공수)에 따라 실제 적용이 달라진다. 4-3을 6종 전부 반영으로 확정했다.
- **회신본 소계 오류는 양식 문제다.** 8개 열이 예외 없이 한 칸씩 밀려 있어 열 삽입/삭제로 범위가 따라 밀린 흔적이다. 특정 파일의 사고가 아니므로 매달 반복될 가능성이 높다. 우리 취합은 소계를 읽지 않아 영향받지 않지만, 노무사에게 별도로 알려 바로잡는 편이 낫다.

## 남은 판단

- 우리 예상 계산을 나이·외국인까지 반영해 정교하게 만들지, 지금처럼 일괄 요율로 두고 회신본 확정에 맡길지. 주민등록번호에서 생년월일과 외국인 여부(뒷자리 첫 숫자 5~8)를 뽑을 수 있어 구현은 가능하다. 다만 예상이 정확해져도 확정은 여전히 회신본이므로, 실익이 확인되기 전에는 손대지 않는 쪽을 권한다.
