# 일용직 근무관리 — 공사건별 노무비 결의서

작성일: 2026-10-14

## 배경

한 달 근무표에는 여러 공사건의 인력이 섞인다. 예: 수의계약 「수도권서부본부 사옥 외부 도장공사」 2명과 「영통1동 청사 냉난방기 추가 설치 공사」 n명.

지금 화면은 공사건을 **화면 전체에 하나만** 고를 수 있고(`LaborPage.tsx`의 `siteId`/`projectId` 화면 상태), 근무자 행에는 공사건이 저장되지 않는다. `labor_records`에는 자유기재 `site_name` 텍스트만 있다. 그래서 공사건이 섞이면 피커를 바꿔가며 체크를 다시 해야 하고, 공사건별로 나눠 올릴 수가 없다.

### 왜 공사건별 1장이어야 하는가

지출결의서는 공사건을 **문서당 하나만** 가진다(`expense_reports.site_id` / `project_id`, 017). 지급줄(`expense_report_payments`)에는 공사건 칸이 없다. 그리고 026이 노무비 결의서에 공사건 연결을 요구한다(CHECK, NOT VALID).

지급줄에 현장 칸을 더하는 설계가 따로 있었다(2026-10-02, 미적용). 2026-10-14에 그 길을 택하지 않았다 — 「검토했지만 택하지 않은 길」 참고.

운영 데이터가 이 구조의 결과를 보여준다 (2026-10-14 조회, 제목에 「노무비」가 든 결의서 최근 10건 중 발췌).

| 제목 | 공사건 |
|---|---|
| 26년 9월 상암오수펌프장 노무비 집행 요청의 건 | 연결됨 |
| 26년 9월 소양농협 노무비 집행 요청의 건 | 연결됨 |
| 26년 8월 연무초,한수중 노무비[김창식,김수만) 집행 요청의 건 | 미연결 |
| 26년 7월 노무비[이희건] 정자1동, 잠원초현장 집행 요청의 건 | 미연결 |
| 26년 7월 아름학교 노무비(인방팀) 집행 요청의 건 | 미연결 |

두 현장을 한 장에 묶은 건은 예외 없이 미연결로 남았다. 10건 중 4건이 미연결이다. 공사건별 1장이면 이 구멍이 닫힌다.

## 결정 사항

2026-10-13 ~ 10-14 대화에서 정했다.

| 항목 | 결정 |
|---|---|
| 결의서 분할 | 공사건별 1장 (2건 → 2장) |
| 공사건 단위 | 근무자 행 1개 = 공사건 1개. 같은 사람이 두 공사건에서 일하면 행을 나눈다 |
| 화면 | 공사건별 섹션형 — 한 표 안에 공사건 구분줄, 그 아래 근무자 행 |
| 상신 | 초안 N장을 한 번에 만들고, 결재 상신은 결의서별로 한다 |
| 입력 경로 | 섹션별 **엑셀 불러오기**가 주 경로다. 손입력도 그대로 쓴다 |
| 엑셀 저장 | 전체 선택 시 **통합 한 시트**. 공사건별로 쪼개지 않는다 |

## 범위 밖 (YAGNI)

- **엑셀 내보내기 시트 분리.** 전체 선택 후 저장하면 **통합 한 시트**로 나가는 것이 요구사항이다(2026-10-14 확인). 공사건은 현장명 열로 구분된다. 현장명 칸에 공사건 이름이 들어가게만 손본다.
- **지급줄 이름에 현장 약칭 붙이기**(`김창식-상암`). 약칭은 사람이 정한다. 이름만 넣고 결의서 화면에서 손본다.
- **날짜 칸별 공사건 지정.** 행 단위로 충분하다(결정 사항).

## 데이터 모델

`supabase/migrations/028_labor_records_work_target.sql` — 017과 같은 패턴.

```sql
ALTER TABLE labor_records
  ADD COLUMN IF NOT EXISTS site_id UUID REFERENCES sites(id) ON DELETE SET NULL;
ALTER TABLE labor_records
  ADD COLUMN IF NOT EXISTS project_id UUID REFERENCES projects(id) ON DELETE SET NULL;

CREATE INDEX IF NOT EXISTS idx_labor_records_site ON labor_records(site_id);
CREATE INDEX IF NOT EXISTS idx_labor_records_project ON labor_records(project_id);

COMMENT ON COLUMN labor_records.site_id IS '입찰/수의 현장. 비우면 공사건 미지정';
COMMENT ON COLUMN labor_records.project_id IS '지원사업 접수 건. 비우면 공사건 미지정';
```

- 기존 행은 채우지 않는다. 전부 「공사건 미지정」으로 모인다. `site_name` 텍스트로 공사건을 **추정하지 않는다**(026이 세운 "site 추정 금지" 원칙).
- 근무표에는 CHECK를 걸지 않는다. 입력 중간에 공사건이 비는 것은 정상이고, 공사건은 결의서를 만들 때만 요구한다. 결의서 쪽 026 제약이 최종 방어선이다.
- `site_name`은 **데이터를 보존한다.** 엑셀 불러오기가 이 값으로 행 중복을 판정한다(`isSameLaborRow`). 화면에서는 섹션 머리줄이 공사건을 보여주므로 행의 「현장명」 칸만 숨긴다.

## 화면

표 머리줄(1~31일)은 맨 위에 한 번. 그 아래로 공사건 섹션이 쌓인다.

```
▸ 수의계약 · 수도권서부본부 사옥 외부 도장공사   2명  실지급 1,250,000원  [근무자 추가] [결의서 만들기] [⋯]
     [v] 김창식 …
     [v] 김수만 …
▸ 수의계약 · 영통1동 청사 냉난방기 추가 설치 공사  1명  실지급 540,000원   [근무자 추가] [결의서 만들기] [⋯]
     [v] 박영수 …
▸ 공사건 미지정                                3명  (!) 공사건을 지정해야 결의서를 만들 수 있습니다
     [ ] (예전 행) …
[+ 공사건 추가]
```

- **「+ 공사건 추가」** — 기존 `WorkTargetPicker`(`src/components/common/`, `compact`/`floating`)로 공사건을 고른다. 고르면 그 섹션이 생기고 **빈 근무자 행 1개를 바로 insert 한다.** 화면 상태로만 들고 있으면 새로고침에 사라지기 때문이다. 이미 있는 공사건을 고르면 새로 만들지 않고 그 섹션으로 데려간다.
- 섹션의 **「근무자 추가」** — 그 섹션의 `site_id`/`project_id`가 자동으로 들어간다.
- 섹션의 **「엑셀 불러오기」** — 주 입력 경로다. 아래 「엑셀 불러오기」 절 참고.
- **행 옮기기** — 행을 체크하면 상단에 「선택한 N행을 공사건으로 옮기기」가 나타난다. 누르면 `WorkTargetPicker`로 공사건을 고르고 그 행들의 `site_id`/`project_id`를 한 번에 바꾼다. 잘못 넣은 행 복구와 기존 미지정 행 일괄 지정을 같은 기능으로 처리한다.
- 섹션 머리줄 **[⋯]** — 「공사건 바꾸기」 하나만 둔다. 그 섹션 행 전체를 다른 공사건으로 옮긴다.
- 섹션 순서는 그 섹션 행들의 최소 `sort_order`. 「공사건 미지정」은 맨 아래 고정.
- 섹션 머리줄에 출처 배지(입찰 / 수의계약 / 지원사업), 인원수, 실지급 소계.
- 상단의 공사건 피커는 **없앤다.** 섹션이 대신하므로 둘 다 두면 어느 쪽이 적용되는지 알 수 없다.
- 상단 총계(총지급액·공제·실지급)는 그대로 둔다.
- 버튼 이름을 「노무비 결재 올리기」 → **「노무비 결의서 만들기」**로 바꾼다. 실제로는 초안만 만들고 상신은 결의서 화면에서 한다.

## 엑셀 불러오기

손으로 치는 것이 아니라 **공사건마다 엑셀을 넣는 것이 주 입력 경로다**(2026-10-14 확인).

- 섹션 머리줄의 **「엑셀 불러오기」** — 파일을 고르면 기존 미리보기 모달(중복 표시·행 골라 넣기)이 그대로 뜨고, 넣은 행에 **그 섹션의 공사건이 자동으로 들어간다.**
- 화면 맨 위의 **「엑셀 불러오기」** — 누르면 **공사건을 먼저 고르는 단계**가 붙고 그 다음 파일을 고른다. 섹션이 아직 없을 때도 불러올 수 있어야 하기 때문이다. 고른 공사건의 섹션이 없으면 새로 생긴다.
- **연·월 불일치 경고** — 엑셀 파일은 연·월을 자기 안에 갖고 있고 지금 불러오기는 그 값으로 행을 넣는다(`parsed.year` / `parsed.month`). 화면이 보고 있는 달과 다르면 **경고하고 확인받는다.** 확인 없이 넣으면 엉뚱한 달에 꽂힌다.
- **엑셀의 현장명은 파일 값 그대로 보존한다.** 공사건(`site_id`/`project_id`)은 섹션 값이고, `site_name`은 파일에서 읽은 값이다. 둘이 달라도 막지 않는다 — 엑셀 양식의 현장명에는 약칭·현장 통칭이 섞여 있다.
- **중복 판정에 공사건을 더한다** — `isSameLaborRow`는 지금 이름·현장명·일급·날짜로 판정한다. 같은 사람이 같은 일급·같은 날짜로 두 공사건에 있을 수 있으므로 공사건이 다르면 다른 행으로 본다.

## 결의서 만들기

- 묶음의 공사건이 그대로 결의서의 `site_id`(입찰·수의) 또는 `project_id`(지원사업)로 들어간다. **026 제약을 만족시키는 지점이 여기다.**
- 상단 **「노무비 결의서 만들기」** — 체크된 행을 공사건별로 묶어 초안 N장.
- 섹션 머리줄 **「결의서 만들기」** — 그 공사건만 1장.
- 확인창에 공사건별 금액을 모두 보여준다.

```
노무비 지출결의서 2장을 만듭니다.
  1. 수도권서부본부 사옥 외부 도장공사   1,250,000원 (2명)
  2. 영통1동 청사 냉난방기 추가 설치 공사   540,000원 (1명)
만든 뒤 결의서를 열어 「결재 올리기」를 눌러 주세요.
```

### 제목 규칙

운영 관행을 따른다(배경의 조회 결과).

1. `{YY}년 {M}월 {공사건} 노무비[{이름들}] 집행 요청의 건`
2. `TITLE_MAX`(50자) 초과 → 이름을 `(N명)`으로 줄인다
3. 그래도 초과 → 공사건명을 앞에서 자르고 `…`을 붙인다

예: `26년 10월 수도권서부본부 사옥 외부 도장공사 노무비[김창식,김수만] 집행 요청의 건`

제목에 공사건이 들어가므로 기존 중복 제목 경고가 공사건별로 제대로 동작한다. 공사건이 빠지면 공사건별 1장이 모두 같은 제목이 되어 매번 경고가 뜬다.

### 만든 뒤 이동

- 1장 → 지금처럼 `/approval/{id}/edit`
- 2장 이상 → `/approval` 목록. 만든 문서를 토스트로 알린다.

### 부분 실패

문서를 한 장씩 순서대로 만든다. 문서 단위 API라 전부-또는-전무로 묶을 수 없다. 중간에 실패하면 **성공한 것은 남기고** 실패한 공사건만 알린다. 다시 누르면 중복 제목 경고로 걸러진다.

## 테스트

순수 함수를 떼어 테스트한다(`src/lib/labor/*.test.ts` 관행).

**`laborGroups.test.ts`**

- 공사건별 묶기: site 2건 + project 1건 + 미지정이 각각 한 묶음
- 같은 사람이 두 공사건에 있으면 각 묶음에 따로 들어간다

- 묶음별 실지급 소계가 `calcRow` 합과 같다
- 미지정 행이 체크되어 있으면 검증이 막는다

**`approvalDraft.test.ts`**

- 제목이 `26년 10월 {공사건} 노무비[이름] 집행 요청의 건` 꼴
- 50자 초과 시 이름이 `(N명)`으로 줄어든다
- 공사건명이 길어 그래도 초과하면 공사건명이 잘린다
- 기존 검증(이름 없음 · 실지급 0원)이 그대로 동작한다

**`importExcel.test.ts`**

- 공사건이 다르면 같은 사람·일급·날짜라도 중복이 아니다
- 공사건이 같고 나머지도 같으면 중복이다

## 검토했지만 택하지 않은 길

`feat/labor-cost-approval` 브랜치(2026-10-02, 미푸시·미적용)에 같은 문제를 다른 자리에서 푸는 설계가 있다.

- 결의서 안에 노무비 전용 작성 화면(`/approval/labor/new`)을 두고, **지급줄마다 `site_id`/`project_id`를 달아 한 장에 여러 공사건을 담는다.**
- `expense_reports`에 `doc_type`·`accrual_month`·`labor_tax_snapshot`, 새 표 `labor_tax_settings`, 월별 신고용 엑셀까지 포함한다.
- 구현계획 1,365줄과 `src/lib/approval/laborTax.ts`(+테스트)가 이미 쓰여 있다. 운영에는 하나도 반영되지 않았다 — `accrual_month`·`line_kind`·`worker_vendor_id`·`/approval/labor`가 모두 origin/main에 없고, 쓰려던 `027` 번호는 `027_leave_carryover`가 가져갔다.

2026-10-14에 **이 길을 택하지 않기로 했다.** 이유:

- 2026-10-09 대표 결정(노무비도 결재를 거친다, 근무관리에서 초안을 만든다)이 이미 운영에 올라가 있고, 그 방향을 잇는 쪽이 변경이 작다.
- 근무관리와 결의서 두 군데에 같은 내용을 입력하게 된다.
- 실제 제목 관행이 공사건별 1장이다(배경의 조회 결과).

그쪽에만 있는 가치 — **월별 신고자료, 작업자 계좌 자동채움, 귀속월** — 는 별건으로 남는다. 이 설계는 그것을 다루지 않는다.

### 공제 범위가 어긋나지 않는 이유

10/02 설계는 소득세·지방소득세·고용보험 3종만 공제하고 후불 공과(국민연금·건강보험·장기요양)는 별도 정산으로 뺀다(`validateLaborApproval`이 이미 막는다). 한편 2026-10-14 현재 근무관리 요율은 **국민연금 0% · 건강보험 0%**(장기요양은 건강보험에서 파생되어 0)로 설정돼 있어 실제로도 3종만 공제된다. 두 접근의 금액이 어긋나지 않는다.

## 운영 메모

- **마이그레이션 적용** — 로컬 017~025와 원격 이력의 타임스탬프가 어긋나 `supabase db push` 전에 repair가 필요한 상태다. 028은 Supabase Studio에서 SQL을 직접 실행하는 쪽이 안전하다.

- 배포는 지시가 있을 때만 한다.
